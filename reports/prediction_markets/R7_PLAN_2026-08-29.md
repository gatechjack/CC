## 7. Q7 — what can bite between "engine restarted" and "first fill reconciled"

- **bitunix bounce:** the restart drops `bitunix_futures`/`bitunix_sfp` (24/7). If bitunix holds open positions, verify
  it re-seeds + reattaches cleanly; a brief coverage gap is the cost (Jack's heads-up). Not PM's bug but PM's restart.
- **Matcher swap:** the engine picks up the on-disk 3-dim matcher (was the old in-memory moneyline copy). If the on-disk
  file differs from what was box-scratched, behaviour changes silently — verify getsource/hash of the loaded matcher.
- **Boot-reconcile latches on a not-clean account:** if the driver runs `reconcile_account` at boot and ANY non-PM
  position remains on the account (exclusivity incomplete, or a stray kalshi_copy_trading fill mid-shutdown), it LATCHES
  -> disarmed -> no order. This is correct (safety), but it means exclusivity must be FULLY clean (0 non-PM positions)
  before arming, not just "kalshi_copy_trading disabled."
- **Empty/failed index or no signal:** if the Kalshi index fetch fails or SDTrading places no new moneyline entry in the
  window, no signal matches -> no order (safe, but the first order simply doesn't happen yet). MLB Saturday games make a
  signal likely within hours, not guaranteed within minutes.
- **Wrong-leg / illiquid strike:** a moneyline copy still resolves to a YES or NO leg; if the matched Kalshi strike is
  illiquid or unquoted, it skips (correct). The NO-leg cost (1−yes) must be right — the lens.
- **IOC 0-fill / benign no-fill:** the marketable IOC may 0-fill if the book moved past the limit ± slippage. Benign (no
  order, retry next signal); do NOT raise the slippage cap to force a fill.
- **Loud reject -> auto-disarm:** an auth/bad-request reject raises `OrderPlacementError` -> the R5 auth-failure /
  consecutive-error latch fires -> account disarmed + open positions flagged for manual exit. Verify the latch behaves.
- **Idempotency:** a crash between POST and journal-write (the K9 window) leaves a real position the journal doesn't know
  — this is EXACTLY what boot-reconcile (now built) catches on the next boot. The idempotency proof (item 6) exercises
  the durable-journal dedup across a deliberate restart.
- **Sign convention:** if unconfirmed and wrong, the fill's reconcile verdict inverts — a placed YES reads as a mismatch
  (spurious latch) or a placed NO mis-nets. The Q4 check must land BEFORE the reconcile in item 4b.

## 13. THE STOP PROCEDURE — operator runbook (the fastest path from "something is wrong" to "orders stopped")

Jack's R7.d ask: *state* the fastest path to stopping orders — the exact command, how long it takes given the
loop's sleep interval, and what survives. This is the emergency-stop reference; it must be understood BEFORE R7.f.

**1. THE COMMAND.** The fastest stop is the CLI disarm — it works even if `pm_web` is down (a standalone script
hitting the persisted state directly), and it needs no web route:
- **One sub-division:** `PYTHONPATH=. venv/bin/python trading_corp/scripts/pm_cli.py live-disarm --account
  kalshi_jack --category mlb`
- **The MASTER kill (ALL accounts + categories at once — use this if unsure):** `... pm_cli.py live-disarm --global`

**2. HOW LONG IT TAKES.** The disarm writes the PERSISTED arm state (legacy `agent_state`) in autocommit —
durable the instant the command returns (sub-second). The driver RE-READS the arm verdict (a fresh `mode=ro`
disk read, no cache) immediately BEFORE EVERY order. So:
- The block takes effect at the **next order boundary**, not the next cycle — a mid-flight cycle is gated
  per-order, so it stops at its very next order.
- Worst-case wait for the next order attempt is bounded by the poll cadence: **`poll_sec` = 7 s default**. Within
  ~7 s the next cycle runs and every order in it is already gated by the fresh disarm.

**3. WHAT SURVIVES IT (the irreducible window).** An order ALREADY POSTed to Kalshi at the moment the kill lands
is **NOT recalled** — that window is **ONE ORDER WIDE** (the per-order re-read → POST gap has no `await` between
it, so at most the single in-flight order lands). Everything after it is blocked. This is irreducible without a
broker-side pre-commit; do not pretend the window closed. To flatten a position already open, the human closes it
**by hand on Kalshi** — the disarm blocks the engine's own exit too (off is off; gates 5/6/8 are exit-exempt for
BUDGET reasons, which is a different question from the kill switch).

**4. IT SURVIVES A RESTART.** The disarm is persisted; a restarted engine comes up DISARMED (the fail-safe
default) and reads the persisted disarm — it does **not** resume placing. Re-arming is an explicit human act
(`pm_cli live-arm`).

**5. THE FOUR AUTOMATIC KILLS (no human needed).** The driver disarms itself + LATCHES on: a **401/403 auth
failure** (disarms the ACCOUNT + flags open positions for manual exit — auth is dead, so the engine cannot place
the reduce_only exit either), **≥3 consecutive order errors**, the **orders/day ceiling** (R7.d wired this — a
runaway can no longer reject-every-poll while showing ARMED), or a **boot-reconcile mismatch** at boot. A latched
auto-disarm STAYS disarmed until a human acknowledges with `pm_cli live-arm --clear-latch` (the operator MUST see
the trigger before re-arming — this guard is structural and now fails SAFE even if the arm row is unreadable).

**6. IF THE CLI CANNOT WRITE (the box DB is locked/broken).** The fail-safe default means an unreadable arm state
reads as DISARMED, and each driver cycle RE-ATTEMPTS a failed auto-latch. The durable backstop if you cannot
disarm via the CLI is to **stop the engine service** (az-root `systemctl stop trading-corp`), which halts ALL
divisions. (A latch-WRITE failure is a known MINOR residual — §14 — the loop retries it next cycle; it is not a
bypass, but it is a reason the box DB health matters.)

**7. VERIFY IT STOPPED.** `pm_cli live-status --account kalshi_jack --category mlb` → `effective_armed: false`;
and `pm_subdivision_order` stops gaining `dry_run=0` rows. `live-status` is read-only and works `pm_web`-down.
