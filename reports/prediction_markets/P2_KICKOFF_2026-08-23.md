## Rulings carried into the build (Jack, 2026-08-23 gate)

These are the findings from the grounding report that Jack ruled on. Treat each as binding.

### (e5) — HARD REQUIREMENT: migration-004 caveat columns must be wired into rollup(), or they read ZERO forever
`stats.rollup()` writes `pm_category_stats` via `INSERT OR REPLACE ... (_STATS_COLS)` — it **rewrites the whole
row every run**. Therefore ANY column added by migration 004 that is NOT also added to `stats._STATS_COLS` **and**
computed in the rollup SELECT is reset to its column DEFAULT (0 / NULL) on every rollup. The new caveat columns
(`two_sided_pct`, `single_game_pct`, `n_condition_ids`, `n_two_sided`, `n_single_game`, `n_futures_like`,
`market_type_source`) and the one-sided companion (`pm_category_onesided_stats`) would silently read ZERO on the
product page, forever — a P1-class silent-wrong-data bug.
**REQUIREMENT:** the migration-004 change ships together with the `_STATS_COLS` + rollup-SELECT extension. The
CP1->CP2 checkpoint MUST run a rollup on real data and VERIFY `two_sided_pct` / `single_game_pct` / the one-sided
slice are POPULATED WITH REAL VALUES — not defaulted. **A zero that could be either real or defaulted is a FAIL
until proven which.**

### (e7) — PINNED NOW: pm_paper_trade.size_basis = FIXED CONTRACT/SHARE COUNT, not fixed dollars
`cost_basis = size_basis * entry_price` only parallels the external side's `cost_basis = total_bought(NOTIONAL) *
avg_price` if `size_basis` is a share/contract count. Fixed DOLLARS would make `cost_basis` mean something
different on the two halves of the same scoreboard — the exact definitional drift that caused the P1
notional-denominator bug. **The migration-005 schema comment must state `size_basis` = fixed contract/share count
so it cannot drift.** (OQ-1 "fixed unit for comparability"; ROI normalizes either way, but the columns' meaning
must match the external side.)

### (e3) — ANALYZE is a COPY of the engine's LLM audit/narration code, and KeyVault access is a PREMISE
`pm_web` has no engine imports, but the audit-building + narration lives in the engine web routes
(`routes.py ~3155-3376`). It must be **copied** into `pm_web` (reuse != coupling, allowed) — not "rewired". And a
second systemd unit reaching the Anthropic key via `KEY_VAULT_URI` + VM managed identity is a PREMISE, not a fact.
**Prove the PM unit can reach the key BEFORE wiring ANALYZE. If it cannot, STOP AND REPORT — do not improvise
credential handling.**

### (e4) — "Do NOT touch ingest.py" means ingest.py ONLY. pm_cli.py and rosters.py are in-bounds.
The roster-source flip (Ruling B) does NOT live in `ingest.py` (which never reads the roster). It lives in
`pm_cli._seed_wallets` + a new `pm_roster` reader in `rosters.py`. Both are PM-package files the plan already
extends (it adds `migrate-roster` / `paper-poll` subcommands to `pm_cli`). "No edits" = engine files + `ingest.py`;
it does NOT cover the rest of the PM package.

### (e6) — P2 ships TWO writers, not three. (e2) — /activity fields verified present.
`P2_PLAN.md` §3.2 lists three cadences; the third ("live marks", seconds) is P3 (plan-the-slot-only). P2 ships the
weekly full refresh + the ~30-min paper-entry poll (+ pm_web's small synchronous writes). `/activity` capture is
real: `PolymarketDataAPIClient.fetch_activity` + `ActivityRow` carry `timestamp` (entry ts), `side` (BUY/SELL),
`price`, `size`/`usdc_size`, `condition_id`, `outcome_index`. CP4 verifies polling behavior + the 5000-row
`/activity` truncation ceiling, not a missing field.
