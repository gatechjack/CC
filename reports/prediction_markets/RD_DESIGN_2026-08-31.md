# R-d — settlement-close path: DESIGN (2026-08-31)

Build BEFORE deploy; ship Option D + R-d in ONE deploy (one restart, one bitunix bounce). Authority = Kalshi's own
settlement record (NOT gamma). Reuse Option D's terminal-close accounting = ONE primitive, TWO triggers.

## 1. THE SHARED TERMINAL-CLOSE PRIMITIVE (one row shape, two triggers)
A position goes flat in the journal via a row with **`is_exit=1`, `outcome_status='filled'`, `fill_count=held`,
`outcome_leg=<held leg>`, `dry_run=0`** -- this is the ONLY shape that nets the signed-net used by BOTH
`boot_reconcile._JOURNAL_SIGNED_SQL` AND `subdivision.live_positions` (verified). Option D's whale-exit produces it
via a POSTed reduce_only order; R-d's settlement produces the SAME shape WITHOUT a POST (the market resolved). The
difference is the TRIGGER, not the state -- so there is one terminal representation, never two.

**The single "is this position still live?" authority = `journal_net_open_contracts(wallet, ticker, leg)`.** BOTH
triggers gate on it: Option D's exit (`skip:not_held` if <=0) AND R-d's settlement-scan (skip if net-open <=0).
That is what prevents a double-close (below).

## 2. SCHEMA -- migration 015 (ALTER TABLE ADD COLUMN, behaviour-neutral like 014)
`pm_subdivision_order` gains: `close_source TEXT` ('settlement' | 'settlement_void'), `realized_pnl REAL`,
`won INTEGER`, `settled_ts INTEGER`. The settlement-close row reuses `fill_price` for the SETTLED per-contract
value (won -> 1.0, lost -> 0.0; void -> avg cost, a refund). Existing rows read NULL -> unchanged behaviour.

## 3. WHAT IT BOOKS (per held wallet x ticker x leg, from OUR journal + Kalshi's result)
- `result` (yes/no/void) from Kalshi's `/portfolio/settlements` (raw payload's `market_result` -- the SDK model
  may drop it, so read RAW, per the standing "check the raw payload" rule).
- `won = 1 if (leg=yes AND result=yes) OR (leg=no AND result=no) else 0`; settled_value/ct = 1.0 if won else 0.0.
- **realized_pnl = net_open * settled_value - cost_basis_open**, where cost_basis_open = net_open * avg_cost and
  avg_cost = (SUM entry fill_count*fill_price + fee) / SUM entry fill_count (average cost, so a partial-exit-then-
  settle is correct; the whale-exit already booked its own leg). CROSS-CHECK vs Kalshi's settlement `revenue`;
  log a WARNING on divergence beyond a fee tolerance (the first settlement -- Cubs -- is hand-inspected via the log).
- Cubs fixture: entry 1 YES @0.60 + fee 0.0084, result=no -> won=0, settled_value=0, realized = 0 - 0.6084 =
  **-0.6084** (matches the transition doc).
- The scan books PER-WALLET (a settlement is market-wide, but each whale's cost basis differs and per-wallet
  net-open must also go flat so a post-settlement stale whale-exit sees `skip:not_held`).

## 4. ★ TRIGGER -- WHERE the check runs + API cost (Jack's question)
- **BOOT-SCAN (mandatory, load-bearing):** at engine boot, BEFORE `run_boot_reconcile`, fetch `/portfolio/settlements`
  once and book any settled held position. **This is what makes the combined-deploy restart come up CLEAN** (books
  Cubs -> journal flat -> reconcile matches the flat venue -> no R-b latch). Cost: **1 API call at boot.**
- **THROTTLED PERIODIC (operational):** re-scan inside the loop on a throttle (default **600s / 10 min**).
  Settlements are infrequent and booking is bookkeeping (NOT time-critical like a trade), so 10-min is ample;
  every-cycle (7s) would cost ~12k calls/day for no benefit. Cost: **~144 calls/day.**
- **RECOMMEND: boot-scan + 600s throttle.** An MLB game we hold ends mid-session -> the position settles -> booked
  within 10 min -> /live + reconcile go flat without waiting for a restart.

## 5. ★ POSITION THAT SETTLES WHILE THE ENGINE IS DOWN (the current Cubs case) -- Jack's question
Handled on the way UP by the boot-scan: it runs BEFORE boot_reconcile, discovers the settled position in
`/portfolio/settlements`, books it, so boot_reconcile then sees the journal already flat and comes up CLEAN --
NOT missed, NOT latched. FAIL-SAFE preserved: if the settlements fetch FAILS at boot, nothing is booked ->
boot_reconcile still sees journal +1 vs flat venue -> latches R-b (the current safe behaviour). So R-d RESOLVES the
drift when it can and FALLS BACK to the latch when it can't.

## 6. ADVERSARIAL (the terminal-close seam)
- **Double-close (whale-exit + settlement):** prevented by the shared net-open guard. Exit first -> net-open 0 ->
  settlement-scan skips. Settlement first -> net-open 0 -> Option D's holding guard skips the exit. One authority.
- **Double-settlement / idempotency:** the held-legs query computes net-open from the CURRENT journal; a booked
  settlement is an is_exit=1 row -> counted in `exited` -> net-open 0 -> the (wallet,ticker,leg) is not re-booked.
  Re-running the scan is a no-op.
- **Wrong realized amount:** computed from OUR journal cost (average-cost) + Kalshi's authoritative result, and
  cross-checked vs Kalshi's `revenue` (WARN on divergence). First settlement logged for hand-inspection.
- **Re-entry of a settled-but-unbooked position:** a settled Kalshi market has no ASK -> the ENTRY path's
  `_leg_ask` returns None -> `skip:no_quote`. Cannot re-enter regardless of booking state. Safe.
- **Unexecuted-path lens (the rung this was born from):** the load-bearing test runs the book path against a fake
  settlements record + asserts boot_reconcile comes up CLEAN -- the path is exercised BEFORE it runs live.

## 7. /live -- stops showing a settled position as held
No template change: `live_positions` drops a ticker when the is_exit signed net is 0, and the settlement-close row
(is_exit=1, fill_count=held) nets it. Proven by a test that seeds the Cubs entry + books the settlement + asserts
the ticker is gone from live_positions.
