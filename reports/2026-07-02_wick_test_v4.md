# Wick-Test v4 — 20-bar price-slope trend filter (GROSS) — VERDICT: FAIL

**Date:** 2026-07-02 · read-only, no prod/live/SFP writes · GROSS only · k=1 causal · 3m · 4 coins.
Branch `wick-test-spike-2026-07-02` (unpushed). Spec `spike_wick_test/PRE_REGISTRATION_v4.md`. Harness
`spike_wick_test/wick_test_v4.py`; run `spike_wick_test/wick_v4_run.log`.

**Single-variable change from v3:** the earn-its-place filter is now a **20-bar price-slope directional trend
filter** (long iff `slope20>0`, short iff `slope20<0`) instead of impulse-displacement. Motivation: v1 refuted
the 15m-EMA200 filter as the *wrong timeframe* for a 3m scalp; a 20-bar 3m slope (~1h) is a timeframe-local
trend that tests the author's "with-trend" precondition on an appropriate horizon. Everything else = v3.

## VERDICT — FAIL (pre-registered, explicit)
**0 of 48 ATR cells pass** (need ≥3 at n≥100, ≥2 coins, both sides, pooled avgR ≥ +0.15R). The 20-bar slope
trend filter **does not rescue the wick test.** Confirms v3: the trend-filter timeframe was never the binding
constraint.

## What the slope filter did
- Keeps **52–61% of fills** (setups where the local 20-bar slope agrees with the trade side). Reasonable
  selectivity.
- **Does not consistently improve avgR.** Slope vs no-filter, same (coin·side·k): sometimes marginally better
  (BTC short 1.0 +0.022→+0.049; BTC long 2.0 −0.045→+0.003), but often **worse** (ETH short 2R +0.243→+0.189;
  ETH short 1.5 +0.116→+0.041; XRP short 2R +0.099→**−0.030**). No systematic gain.
- **No slope cell beats its null.** The null for slope cells is **slope-matched** (random entries drawn from
  same-slope bars) — and every positive slope cell falls short (e.g., BTC short 2R slope +0.087 vs null +0.096;
  ETH short 2R slope +0.189 vs +0.274; SOL short 1.5 +0.041 vs +0.191). Random entries in the *same slope
  regime* profit equally from the trend/drift, so **the wick pattern adds nothing beyond the slope timing** —
  and the slope timing is mostly the bear drift. (The cells also fail the looser all-bars direction-matched null
  used in v3, so the conclusion is robust to the null choice.)
- **Longs remain negative everywhere** (best BTC long 2.0 slope +0.003, fails null) → both-sides gate fails.

## Why it fails — same two reasons as v3, now with the trend-timeframe excuse removed
1. **The entry is anti-selective.** DR-skip diagnostic is unchanged (skip set is filter-independent):
   triggered-but-unfilled setups would have been **+0.76/+0.58/+0.45R** (k=1.0/1.5/2.0). The retest requirement
   still discards the winning runners; no trend filter fixes an entry that removes the winners.
2. **The short "edge" is bear-beta.** Drift BTC −4.5% / ETH −33.4% / SOL −24.4% / XRP −29.3%. The slope-matched
   null embeds the trend; short cells underperform it → they read as beta, not alpha. Filtering *by* the slope
   just concentrates the same beta the null already captures.

## Ledger
The wick test stays **retired**; v4 is a confirming data point: **changing the trend definition from 15m-EMA200
(v1) to a 20-bar 3m slope (v4) does not help**, because the trend filter was never the binding constraint — the
entry mechanic (anti-selective to runners) and the bear-beta of the short positives are. Four independent
constructions (v1/v2/v3/v4) fail to produce a null-clearing, both-sides, multi-coin gross edge on this 47–81d
bear-dominant window.

## Caveats
47–81d one-bear-regime; GROSS only; DR-skip would-have-been is forward-conditioned (diagnostic, not tradeable);
literal-stop cells are reference (not gated). No lookahead: slope20/ATR/regime/impulse read from closed bars;
DR fill and sims strictly forward, stop-first.
